# Chrome 확장 제어 안정성

## 확인된 원인

Codex Chrome 확장과 Native Messaging Host의 설치·레지스트리·허용 origin은 정상이다. 연결이 끊긴 것처럼 보인 직접 원인은 다음 세 가지였다.

1. 복원된 대형 조립공장 화면에 전체 DOM 읽기처럼 30초를 넘는 명령을 보내 브라우저 제어 클라이언트가 시간 초과됨
2. 시간 초과 또는 커널 재시작 전에 얻은 탭 핸들을 새 세션에서 다시 사용함
3. 여러 탭 제어·닫기 요청을 병렬로 보내 단일 Native Messaging 연결에 요청이 겹침

진단 당시 Native Host 프로세스는 브라우저 제어 클라이언트가 시간 초과된 뒤에도 살아 있었다. 따라서 확장 설치 실패가 아니라 제어 요청 수명과 탭 핸들 관리 문제다.

## 고정 운영 방식

- 프로필: Chrome `Default` / 표시 이름 `호야`
- 연결: 공식 Codex 확장 연결 하나
- 실행: 모든 Chrome 명령 직렬 처리
- 읽기: 전체 DOM 대신 selector 단위의 작은 상태만 조회
- 활성화: 로컬 앱의 일반 버튼은 고유 locator 확인 후 `Enter`
- 시간 초과: 기존 탭 핸들 폐기 후 새 앱 탭 하나에서 checkpoint 재개
- 정리: 작업 끝에서 한 번의 `tabs.finalize`

이 방식은 물리 마우스 포인터를 움직이지 않으며, 사용자 탭·생산관제 worker 탭을 건드리지 않는다.

## 검증 기준

연결 안정성은 다음 순서가 한 세션에서 연속 통과할 때만 인정한다.

1. `tabs.list()` 성공
2. 최신 앱 탭에서 짧은 상태 읽기 성공
3. 조립공장과 DB 탭 활성화 성공
4. 신화사DB·Cafe24 후보 버튼 각각 한 번 활성화
5. 두 버튼이 `확정됨`으로 바뀐 것을 read-back
6. 새로고침 두 번 뒤 작업파일·제품명·기본 이미지·후보 선택 유지

격리 실제 포인터 검증은 회귀 ID `DB-10`이 담당한다. 사용자 Chrome 검증은 외부 등록·삭제·유료 생성 없이 읽기와 내부 후보 선택까지만 수행한다.
